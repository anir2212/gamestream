# GameStream

GameStream is a local pipeline for game telemetry. A producer writes versioned Avro events to Kafka; Spark keeps the raw frames in an Iceberg bronze table and decodes, validates, and deduplicates them into silver. The goal is to make retention and funnel queries possible even when client schemas evolve or events are delivered twice.

I built this as a fault-aware lab rather than a production service. The events are generated, and each measured stage is recorded in [RESULTS.md](RESULTS.md). On 22 October the whole local stack ran together once: producer, Kafka, Spark bronze and silver, Iceberg, Trino and dbt, ClickHouse, Airflow and Superset.

## What has run

- A one-broker smoke round-tripped 1,020 Avro deliveries using both schema versions.
- A separate three-broker test recovered all 200 acknowledged keys after broker stops. It is one small fault experiment, not a durability guarantee.
- A staged run used PostgreSQL for Iceberg catalog metadata, MinIO for table data, and a persistent PostgreSQL store for Apicurio schemas. A catalog smoke wrote and read one row. Later table readback found **2,142 bronze deliveries** and **1,003 distinct silver event IDs**. Most events in the final publish were too old for the silver watermark, so these counts are not throughput figures.
- Trino independently read those same Iceberg counts. A live dbt build created eight models and passed 23 data tests; the separate silver quality gate found no invalid rows among 1,003 records.
- A manual January 1 backfill recovered 97 watermarked-out event IDs into silver, raising it to 1,100 unique rows. Replaying the same date added no rows. Trino DQ and all 31 dbt build nodes passed again after the change.
- In a separate ClickHouse stage, a fresh 1,020-delivery Avro fixture produced 1,000 distinct served events. Both schema versions decoded, and the minute aggregates agreed on 1,000 events and 34 purchases.
- **22 October, full stack.**
  - **Same events in both stores.** The versioned `parity-v1` fixture regenerated byte-identical and reached both stores. The benchmark only times queries after both engines return the manifest's answers, and it passed ([report](bench/query_bench_parity-v1_2026-10-22.json)).
  - **Restart.** A silver crash injected right after a MERGE replayed without adding rows.
  - **Airflow.** The daily DAG ran the quality gate and the dbt build after one fix: dbt now writes its logs and target outside the read-only project mount.
  - **Superset.** `scripts/superset_dashboards.py` built both dashboards, checked every chart returned rows and exported them ([dashboards](superset/exports/), passwords masked by Superset).
  - **Date filters, 23 October.** Each dashboard has a native event-date filter scoped to all its charts. Restricting it to 1 February cut each minute chart from 1,446 to 646 rows with data, and the purchase funnel, retention and DAU charts to that one day. Headless Chrome confirmed every chart request carried the chosen range ([evidence](bench/dashboard_filters_2026-10-23.json)).
  - **Stale checkpoint.** Bronze's old checkpoint pointed at offsets that Kafka's 24-hour retention had deleted, so it was restarted on a new checkpoint path.

  The run's record is [bench/live_checklist_2026-10-22.json](bench/live_checklist_2026-10-22.json).

An earlier attempt hit a Hive 4.0.1 / Iceberg 1.10.0 Thrift incompatibility. The JDBC catalog removed that blocker for Spark and Trino. The staged ClickHouse counts from 19 October used a different event set from Iceberg; the only fair speed comparison is the 22 October `parity-v1` run.

## Run a bounded local check

You need Docker Desktop, Python 3.12, `uv`, and enough disk space for the Kafka and Spark images. Install the Python dependencies and run the local tests first:

```sh
uv sync --extra test --extra spark --extra analytics
make test
make lint
```

For the small Kafka/registry smoke, use `make up-small`, `make topic-small`, `make smoke`, then `make down-small`. For the staged lakehouse path:

```sh
make up-core
make lakehouse-init
make catalog-smoke
make bronze
make silver
uv run gamestream-produce --count 1000 --brokers 127.0.0.1:19092 --registry http://127.0.0.1:18081/apis/ccompat/v7
make verify-lake
make down
```

The streams start in the background; wait for their first commits before running `make verify-lake`. The 18 October run reused a cached Spark image with `--no-build`, so it needed the newer verification script copied into that container; `make up-core` rebuilds the image for a fresh run. Keep the Kafka and registry volumes together when resuming a retained topic. The larger `make up` profile adds the analytics and UI services. It ran together once on 22 October, but it is not a one-command demo: the stages above still need to be started and checked in order.

After the core stage has committed data, the analytical stage can run with only the catalog database, MinIO, and Trino:

```sh
docker compose -p gamestream-full -f compose/compose.yaml --profile full --profile lakehouse up -d --no-build metastore-db minio trino
cd dbt && ../.venv/bin/dbt build --profiles-dir . --no-partial-parse --threads 1
cd .. && GAMESTREAM_TRINO_HOST=127.0.0.1 GAMESTREAM_TRINO_PORT=18082 .venv/bin/python -m dq.run_checks
make down
```

The 18 October run stopped Kafka and Spark before dbt to leave memory for Trino. Keep the existing named volumes; this sequence assumes the earlier core stage committed bronze and silver data.

For a small ClickHouse check, start the three brokers, registry, and ClickHouse, then publish a fresh fixture:

```sh
GAMESTREAM_VOTERS='1@broker1:9093,2@broker2:9093,3@broker3:9093' GAMESTREAM_RF=3 GAMESTREAM_MIN_ISR=2 \
  docker compose -p gamestream-full -f compose/compose.yaml --profile full --profile lakehouse up -d --no-build broker1 broker2 broker3 registry clickhouse
make smoke
.venv/bin/python bench/verify_clickhouse.py --expected-unique 1000
make down
```

Wait for the Kafka consumer to catch up before running the verifier. It checks unique IDs, both Avro versions, v1's absent device field, and the minute aggregates. The saved counts are in [the ClickHouse stage record](bench/clickhouse_stage_results.json). `bench/query_bench.py` times queries only when both sinks hold the same fixture IDs and return the manifest's answers; it refuses a mismatched run.

The manual backfill is limited to 31 inclusive event dates. It scans bronze across arrival dates before selecting decoded event dates, so a record that arrived much later is still eligible for recovery. That choice is safer for this small lab but would require an indexing or lateness policy at larger scale. Local tests cover the date bound, selection logic, and Spark cleanup after failure. The one-day Iceberg backfill and same-date replay passed on saved synthetic data. The silver streaming restart passed on 22 October; the Airflow backfill DAG has not been run. Stop the silver writer before running the manual backfill against the same table.
